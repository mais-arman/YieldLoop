# YieldLoop — Complete UI, Workflow, Actor, and Original Requirements Audit

## Objective

Produce a detailed, evidence-based inventory of the CURRENTLY IMPLEMENTED YieldLoop application so its owner can understand exactly what exists, how every page works, which role uses it, what text and controls it contains, and how well it satisfies the original Ibn Khaldoun Printing and Publishing challenge.

This is a read-only application audit.

**Do not redesign, implement, refactor, delete, rename, or change application functionality during this task.**

Inspect the actual codebase, routes, frontend components, backend APIs, permission rules, existing documentation, and current UI wherever access is available.

Create one detailed report at:

`docs/yieldloop-current-application-inventory.md`

You may create or update this report file only. Do not modify application source, configuration, dependencies, migrations, or database records.

## Skills

Follow:
- `yieldloop-domain`
- `yieldloop-engineering-quality`
- `yieldloop-design-system`
- `yieldloop-cutting-studio`

Use these skills to understand the intended rules, but do not assume the implementation follows them. Verify the current implementation directly.

Inspect the actual frontend routing configuration and produce a complete list of all routes currently registered in the application.

Include:
- Login and authentication pages.
- Main application pages.
- Dashboard and overview.
- Production Jobs list.
- Production Job detail and associated sections.
- Material recording and reconciliation.
- Inventory and offcut details/history.
- Reports and job comparison.
- Cutting Studio and saved-plan/history views.
- AI or Production Assistant.

- Password-change/account pages.
- Not-found, access-denied, and other relevant error pages.
- Any 3D packaging designer, prototype, or experimental route if one actually exists.

Do not invent pages that only appear in documentation or previous plans.

For each page or route, record:

1. Exact URL/path.
2. Page/component name.
3. Whether it is actually registered and reachable.
4. Whether authentication is required.
5. Which roles may access it according to the actual backend authorization rules.
6. Whether the route is protected only in the frontend or also by the backend.
7. The file paths implementing it.
8. Whether it is functional, partially implemented, unavailable, or merely a placeholder.

Also identify routes that redirect, duplicate another page, have no navigation link, or appear obsolete.

# PART 2 — ACTOR-BY-ACTOR PAGE INVENTORY

The application has exactly three approved application roles:

1. Cutting Operator
2. Production Supervisor
3. Manager

For EACH role, document every page that the user can access and the order in which the navigation presents those pages.

Create a separate page inventory for each actor.

Do not assume the three actors should see the same pages. Report the actual implementation, then identify differences between what is implemented and what appears appropriate for the original factory workflow.

For every page available to a role, provide the following details.

## A. Page identity and purpose

- Page name as shown to the user.
- Exact route.
- What problem the page solves.
- Why this actor needs the page.
- What action the user is expected to take there.

## B. All visible text

Transcribe the actual visible interface wording as completely as possible.

Include:
- Page titles.
- Subtitles and descriptions.
- Cards and metric labels.
- Filter labels and default values.
- Table column headers.
- Buttons and action labels.
- Form field labels and placeholders.
- Help text, tooltips, and explanatory notes.
- Empty-state messages.
- Validation and error messages available in the implementation.
- Success messages and confirmation dialogs.
- Pagination wording.
- Status labels and badges.
- Technical notices.
- All visible AI availability/unavailable messages.

Record Arabic and English wording separately where both translations exist.

Do not replace exact existing wording with a summary. The owner needs to understand what the application currently says.

If a label is dynamically generated, show its template and one actual example when safely observable. For example, if a generated timestamp or a selected-filter summary is displayed, record its format and purpose.

Never include passwords, tokens, API keys, private credentials, or other secrets in the report.

## C. Page layout and hierarchy

Describe the actual layout:

- Header and sidebar/navigation.
- Main content width and organization.
- Number and order of content sections.
- Cards, charts, tables, forms, panels, dialogs, and tabs.
- Which information appears above the fold.
- What requires vertical or horizontal scrolling.
- Mobile/tablet layout changes.
- Arabic RTL versus English LTR behavior.
- Loading, empty, error, and success layouts where implemented.

Identify redundant content, duplicated information, excessive text, unnecessary status panels, unused whitespace, clutter, or unclear visual hierarchy. Explain the user impact of each problem rather than saying only that the page looks bad.

## D. Controls and interactions

For every visible interactive element, explain:

- What happens when it is clicked, selected, submitted, opened, or changed.
- Which API request or frontend operation it triggers, if any.
- Whether the action actually works in the current implementation.
- Whether the control is disabled under certain conditions.
- Whether permissions affect its visibility or execution.
- Whether the result is saved to PostgreSQL or is only temporary frontend state.
- Whether an audit event or revision is created for important changes.
- Whether the action has a confirmation, validation, loading state, or error recovery.

Explicitly identify dead buttons, placeholder interactions, controls that only look functional, and UI actions that have no actual backend implementation.

Do not claim a control works simply because a handler exists. Verify the implementation path, and use safe browser observation where possible.

## E. Data displayed

For each metric, table, chart, and record summary, explain:

- Exact field or backend endpoint supplying the data.
- Whether the data is live, persisted, derived, hardcoded, mocked, or unavailable.
- The calculation formula for derived values.
- Units and number formatting.
- Filter and date semantics.
- How corrected, voided, or superseded records are handled.
- How zero denominators or missing values appear.
- Whether the same information is duplicated on other pages.

For charts, document the actual datasets, series, axes, legends, and underlying calculations where available.

For cutting metrics, clearly distinguish geometric utilization, unused board area, material weight, good yield, scrap rate, and reusable offcuts.

# PART 5 — ORIGINAL IBN KHALDOUN CHALLENGE COMPLIANCE

Use the exact original challenge brief as the baseline:

- Digital job card.
- Material and cutting machine selection.
- Issued board weight.
- Good product output.
- Scrap by reason.
- Reusable offcuts separated from scrap.
- Rework recorded separately when applicable.
- Automatic material-balance validation.
- Yield and scrap calculations with explicit definitions.
- Same-machine job comparison.
- Access to supporting records behind the difference.
- IK-202 and IK-203 demonstration data.
- Correct setup/layout versus damaged scrap breakdown for IK-202.
- Correctly unspecified scrap reasons for IK-203 when source data does not provide a breakdown.
- Optional evidence-based AI assistance that suggests investigation without asserting an unverified root cause.
- Factory demonstration that reproduces the calculations.

For every requirement, assign exactly one status:

- **PASS — Verified:** implementation and evidence confirm the requirement works.
- **PARTIAL:** some functionality exists but the entire requirement is not satisfied.
- **MISSING:** no working implementation was found.
- **UNVERIFIED:** evidence is insufficient to establish the actual behavior.

For every status, cite the specific page, component, API endpoint, test, or persisted demonstration record supporting the conclusion.

Do not mark a feature PASS merely because its name appears in documentation, a button exists, or a mock response is displayed.

Explicitly verify the expected case results:

IK-202:
- Issued: 1,200 kg.
- Good output: 900 kg.
- Setup/layout scrap: 180 kg.
- Damaged scrap: 60 kg.
- Total scrap: 240 kg.
- Reusable offcuts: 60 kg.
- Variance: 0 kg.
- Scrap rate: 20%.
- Good yield: 75%.

IK-203:
- Issued: 1,000 kg.
- Good output: 820 kg.
- Scrap: 100 kg.
- Reusable offcuts: 80 kg.
- Variance: 0 kg.
- Scrap rate: 10%.
- Good yield: 82%.

Comparison:
- Both use CT-2.
- Scrap-rate difference: 10 percentage points.
- Good-yield difference: 7 percentage points.
- The 180 kg setup/layout entry is the largest recorded scrap category in IK-202, not proof of an established root cause.

If the records have been changed since the previous reports, report the actual current values and do not modify the data to force it to match.
