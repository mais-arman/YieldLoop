Implement Phase 5: **Offcut Inventory & Reuse** for YieldLoop.

Before coding, inspect the existing domain skills, `docs/phase-4.md`, current material and reconciliation models, job lifecycle, authentication, permissions, audit implementation, and existing tests. Treat the current Django backend and PostgreSQL database as authoritative. Do not use the unused Express/Drizzle starter for business logic or schema.

## Goals
Create a traceable inventory of reusable offcuts generated by production jobs, and allow eligible offcuts to be reserved and consumed by another eligible job without losing their history.

## Important domain constraints
- Phase 4 currently records one material per job and quantities in kilograms to three decimal places.
- Do not invent physical dimensions, material grades, density, thickness, or unit conversions.
- Before implementing reuse matching, determine which offcut attributes are already captured and which are required to safely identify compatible material.
- If essential compatibility information is missing, implement the safe inventory foundation and report the missing factory decisions rather than fabricating values or claiming that an offcut is suitable.
- Preserve Phase 4 accounting definitions and persisted reconciliation snapshots. Do not silently rewrite historical measurements.
- Keep unexplained variance separate from scrap and reusable offcuts.
- Do not allow the same offcut quantity to be consumed or reserved more than once.
- Use exact Decimal arithmetic, database transactions, appropriate row locking or equivalent concurrency protection, idempotency protection where applicable, and append-only audit history.

## Inventory behavior
1. Create traceable inventory records linked to their source job and original reconciliation/output record.
2. Define explicit inventory states and valid transitions, including available, reserved, consumed, and voided where appropriate. Document the transitions and enforce them server-side.
3. Support partial quantities only if the model can preserve accurate remaining balances and traceability.
4. Provide a transaction history showing additions, reservations, releases, consumption, and authorized corrections.
5. Prevent voided, consumed, incompatible, or insufficient-balance inventory from being reused.
6. Where compatibility rules are not yet defined, do not present an offcut as a confirmed match. Make the limitation clear in the UI and API.
7. Do not automatically alter a job's reconciliation figures when inventory is reserved, released, or consumed. Define and document the accounting implications; if a policy decision is required, stop short of inventing it.

## Permissions
- Enforce authorization in the backend, not just in the frontend.
- Manager and Production Supervisor may perform inventory operations within their authorized scope.
- Cutting Operator remains read-only for inventory unless existing approved domain rules explicitly permit otherwise.
- Respect existing job permissions and lifecycle rules. Draft and Cancelled jobs must not accept prohibited writes.
- Every mutation must record the actor, timestamp, reason when applicable, and relevant source/target job references.

## User interface
- Add a bilingual Arabic/English inventory page consistent with the existing design system.
- Include paginated inventory, useful filters, clear status indicators, loading skeletons, empty/error states, and readable mobile layouts with correct RTL/LTR behavior.
- Provide an inventory detail/history view.
- Only show reserve/consume actions when the backend permits them.
- Do not build a cutting optimizer or claim physical fit in this phase.

## Tests and verification
Add tests for Decimal precision, partial consumption and remaining balances, duplicate requests, concurrent reservation/consumption, invalid state transitions, permissions, cross-job references, cancelled jobs, audit history, and transaction rollback. Test compatibility restrictions explicitly.

Run the relevant backend tests, lint, migration-drift checks, workspace typecheck, frontend lint/build, and appropriate browser checks. Use an isolated PostgreSQL test database. Apply migrations only to a positively verified development database using the existing safety guard. Never weaken the guard, run production migrations, or add startup migrations.

## Scope exclusions
Do not implement dashboards, report exports, cutting optimization, AI, voice, deployment, or multi-tenant onboarding in this phase.

## Final report
Summarize the implementation, migration target, inventory state transitions, permission matrix, tests and results, and unresolved factory decisions. Clearly distinguish implemented reuse tracking from any future dimension-based compatibility matching. Stop after Phase 5.
